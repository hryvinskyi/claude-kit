# Engineering standards

## Text other people read never cites agent config
In a PR review comment, issue, evidence comment, commit message, doc or chat post, never name `CLAUDE.md`, `AGENTS.md`, anything under `.claude/`, a skill or agent memory as the source of a rule ("The root CLAUDE.md requires tests…"). Teammates don't work from those files, and quoting them reads as a bot quoting its prompt. State the rule as the project's own and give the concrete reason it matters ("integration tests boot the real kernel and Postgres, so a stub never runs this SQL"). When a subagent or skill will post such text (`/code-review --comment`, issue creation), tell it this in the brief, and grep its text for `CLAUDE|AGENTS|\.claude/` before it goes out.

## Knowledge vaults
A project's vault is whatever `find-vault` (the `vault` plugin's command on `PATH`) resolves. Three global tools serve every vault project. A project whose own `.claude/settings.json` declares a SessionStart or SessionEnd hook is left to its own tooling for that event.
- **Search the vault before re-deriving anything.** Use the `qmd` MCP tool `query`; it searches only the current project's index. Each project gets its own index in `.qmd/`, created in the background on its first session and excluded through `.git/info/exclude`. Grep when qmd is not connected. A hit is where to start reading, never a fact to repeat.
- **`vault-check`** holds living notes (Modules/, Bridges/, Plugins/, Kernel/, Runbooks/, the `00 …` overview) to the code.
  - A class or path they cite that exists nowhere, or a broken wikilink, is a hard finding. Fix the prose. Strike a name through (~~`Old`~~) only when the sentence is about its retirement.
  - A cited file that changed since its paragraph was stamped is a soft finding. Rewrite the paragraph, or `--stamp <note>` when it still holds.
  - There is no exclusion list and no baseline.
- **At session end**, the `vault` plugin's capture hook (`vault-capture` when run by hand) does three things:
  - files a session that committed work without a journal entry into the vault's inbox (the brief's `[INBOX]` line names the file; `/vault:journal` clears it);
  - refreshes the stamps and the search index;
  - commits and pushes **only a vault that is a git repository of its own** — never a project's repository.
- **Nothing is written into a project's tracked tree.** A vault that is neither its own repository nor ignored by the project keeps its inbox, stamps and caches under `~/.claude/state/vaults/<project>/`.
- **`[VAULT] no copy off this machine`** means the vault has no backup. Giving it one creates a remote, which is an outward action: propose it and wait for a yes. The steps are `git -C <vault> init`, a private remote, then a push; if a project encloses the vault, exclude it with `.git/info/exclude`. Never back up a client project's vault to a personal account without asking.
- Kill switch: `CLAUDE_NO_VAULT_TOOLS=1`.

## Architecture and tech debt
Binds every stack and every workflow — an ad-hoc edit, a bug fix, a review that applies fixes, a `/pipeline:feature` plan. Not only PHP, not only planned work.
- **Code is written clean, always.** The dependency rule (inner layers never import outer concretes — framework, ORM, HTTP, `ObjectManager`), SOLID, business rules inside the domain model, ports owned by the inner layer, humble delivery mechanisms that only translate and delegate, behavioral dispatch through injected polymorphism instead of `switch`/`elseif`-on-type. The `architecture:clean-architecture-php` skill (PHP: Symfony, Magento) and the `architecture:clean-architecture-js` skill (JavaScript and TypeScript: framework-free modules, React, Node, and the browser code Magento and Symfony ship — RequireJS/Knockout, Hyvä/Alpine, theme-assets scripts, Stimulus, islands) are the canonical statement of the bar; on another stack apply the same lenses in that stack's idiom, and load the project's own rubric when it declares one. New code never adds debt: no new suppression, baseline entry, skipped test, god class or Helper.
- **PHP: code never writes `new SomeClass`.** That covers a framework value (a translatable message, a response), a value object, and a static named constructor that hides `new self(...)`. An object a class needs comes from an injected collaborator typed on an interface: a service from the container, or a factory interface whose implementation the build generates, so `new` appears only in generated code. A `new` binds the caller to a concrete class and its construction — the dependency rule broken at the call site, with nothing able to substitute it — so in every plan, fix and review it is a defect, and a named constructor is never offered as the clean alternative. Exempt: `throw new …Exception`; tests; the composition root, where no container exists yet (`new Kernel(...)` in the front controller or the console entry point); `(object) []` as an empty JSON object, and as nothing else. A hand-written factory with `new` inside is never allowed, not even where the stack has no factory generator: there, how the object is created becomes a decision of the plan. Other stacks build values in their own idiom (Rust: `Type { .. }`, `Type::new`, `Type::parse`); what binds on every stack is the dependency rule — every port is injected at the composition root, and no use case or domain code names an adapter type.
- **Tech debt inside the blast radius is fixed in the same change, always.** Blast radius = the files you change plus their direct collaborators in the same module (one hop: what they call and what calls them); the whole module when it is small (about fifteen classes) or the change already touches most of it. Debt is: dependency-rule violations, anemic models and stranded business rules, god/Helper/Util classes, `switch`/`elseif` dispatch by type, leaky boundaries (entities crossing an API), misplaced resources (a module's config/translations/migrations in a sibling), fat interfaces, missing or mocked-DB tests for code you change, deprecated APIs, suppressed static-analysis errors. `SKILL.md` §*In-scope tech debt* has the full list and the plan format.
- **Never deferred.** No `TODO`/`FIXME`/`HACK` comment, no "later" for in-scope debt, no baseline or suppression to get a gate green. Every fix ships with its own tests at every level the project mandates and keeps the gates green; a big fix becomes ordered tasks inside the same change, never a follow-up. The `guards` plugin's `debt_guard.py` blocks an edit that adds a deferral marker or a suppression to a source file, or that grows a static-analysis baseline; its `bash_guard.py` applies the same check to text written through the shell (a redirect, `tee`, `sed -i`) and blocks regenerating an existing baseline. Scripted writes (a python/php one-liner) are not seen by any hook; the rule binds them all the same.
- **Debt is fixed through the rubric, not from memory.** Before the first edit of a change that fixes debt or moves a seam (a class another module touches, a port, an entity, a cross-module contract, a service registration), load the architectural skill with the Skill tool **and its references** (`references/<name>.md` in the directory the Skill tool reports for the skill) — `SKILL.md` alone is not the rubric. PHP: `architecture:clean-architecture-php` with the stack reference (`magento2.md` / `symfony.md`) and `solid.md`; `ddd.md` when an entity, value object, aggregate or Magento `Api/Data` type is touched; `clean-architecture.md` / `onion-modules.md` when a boundary, port or module placement is in play. JavaScript/TypeScript: `architecture:clean-architecture-js` with `solid.md`, `javascript.md` and the host reference (`react.md`, `magento2-frontend.md`, `symfony-frontend.md`); `typescript.md` for TypeScript; `ddd.md` for a domain module; `clean-architecture.md` when a boundary, port or feature placement is in play. A change that touches both loads both. On another stack the project's own rubric, and say so when it has none. Work in the skill's order: name the smell (Review mode), design the fix domain-outward (Plan mode, scaled to the size of the fix), then edit. The `guards` plugin's `plan_skill_gate.py` refuses a PHP or JS/TS source edit, not only a plan file, until the session shows the skill and the references that target needs, and names the missing ones; its `bash_guard.py` applies the same gate to source written through the shell.
- **A module names only what it depends on.** Code, docblocks, comments, templates and wiring of a module never mention a module, vendor or product it does not declare (`module.xml` sequence, `composer.json` require, `package.json` dependencies). A neighbour's quirk you are working around is described neutrally — the situation, not the neighbour: *"a checkout flow that fires the success event on a request without a success page"*, never *"such as Acme One-Step Checkout's payment return"*. The name of the neighbour goes in the vault or the journal. If the coupling is real, declare the dependency first, then name it. No hook checks this — a word cannot be told from a vendor mechanically — so it is reviewed: the `/pipeline:feature` verify phase greps the diff for vendor names, and `pipeline:devils-advocate` reads task wording for it.
- **Debt outside the blast radius is never silently passed over.** Name it in the final message and put one line on the vault's TODO board (or the plan's *Logged for later*). It enters scope the moment the user says so; do not widen the change on your own — a feature is not a licence to refactor a module, and widening is the user's call. If an in-scope fix forces a change in a neighbouring module, say so and ask, don't sprawl.
- If the user asks for a patch that would leave in-scope debt in place, say which debt stays and why it matters, then do what they decide.

## Tests run code
Every stack, every workflow, and every place above that asks for tests — "tests at every level the project mandates" is satisfied by tests that execute something.
- **Never write a test that reads a project file and asserts its text or structure**: parsing `di.xml`/`config.xml`/layout XML/`services.yaml`, grepping a template or script for words, copying a config table or translation file into an assertion. Such a test pins formatting rather than behaviour, guards one module while the same fault passes everywhere else, and stays green while the application is broken.
- Wiring (a DI preference or argument, a plugin, an observer, a layout block, a service tag) is proven by what consumes it: an integration test through the real container or a real render, or the build step that reads it (`setup:di:compile`, a container compile, a production-mode deploy). If only that build step would catch a fault, say so and name the check — do not stand in for it with a file-reading test.
- One met inside the blast radius is deleted, not extended.

## PHP static analysis
- PHPStan always runs at **level 10** (the maximum). Pass `--level=10` on the command line, or set `level: 10` in the project's `phpstan.neon` / `phpstan.dist.neon`, whichever the project uses. Never analyse at a lower level to make a run pass.
- **Level 10 is mandatory for code you write or change** — every new file, and every file you edit, must come out of `--level=10` clean. That includes the types you add: no `mixed` left where a real type is knowable, no `array` without a shape or value type.
- **Legacy code outside the blast radius is out of scope** until a change reaches it (*Architecture and tech debt* above defines the radius). That is the only thing a baseline is for: it freezes errors that already existed. Once a legacy file enters the blast radius, the code you changed leaves the baseline — delete its entries and fix them at level 10; suppressed errors in its direct collaborators are in-scope debt and go the same way. Untouched parts of that same file may stay baselined; if fixing them would balloon the diff, say so rather than doing it silently.
- **Never grow the baseline.** Regenerating it to absorb an error your change produced is the one thing this rule forbids. Same for `@phpstan-ignore*` on new or edited code — fix the type, or report the error as unfixable and explain why.
- Level 10 requires PHPStan **2.x** — 1.x stops at level 9. If a project pins `phpstan/phpstan: ^1.*`, say so instead of silently analysing at a lower level.

## JavaScript and TypeScript static analysis
- TypeScript you write or change type-checks clean under the project's `tsconfig` with `strict` on, through a gate that actually type-checks (`tsc --noEmit` or the project's equivalent — bundlers that strip types check nothing). A project that runs looser gets stricter settings for new code the way it supports that (a stricter `tsconfig` for the new directory, `// @ts-check` with JSDoc on JavaScript), never looser ones for yours.
- **Never loosen the config to make a run pass**: no `strict: false`, no new `exclude` for the file that fails, no `checkJs: false`, no lint rule switched off. Same for `any`, `as unknown as`, `@ts-ignore`/`@ts-expect-error`/`@ts-nocheck` and `eslint-disable` in new or edited source — fix the type, or report the error as unfixable and explain why.
- The project's linter runs clean on the files you touch. ESLint's bulk-suppressions file (`eslint-suppressions.json`) is a baseline: it only shrinks — the `guards` plugin's `debt_guard.py` refuses an edit that grows it, its `bash_guard.py` refuses `eslint --suppress-all`/`--suppress-rule` over an existing one.
- Legacy JS/TS outside the blast radius is out of scope until a change reaches it — the same rule as the PHP baseline above.
